# Integration Setup & Scaling

**Status:** Built (Phases 1–3)  
**Date:** 2026-03-03  
**Updated:** 2026-07 (Smart Home product connect via Smart Home panel; contributor CLI `task setup:home` remains for bootstrap/onboard)
---

## Problem

Adding external integrations to JARV1S has an unacceptable setup cost. The Google Calendar integration took ~4 hours: create a Google Cloud project, enable the API, configure OAuth consent, create Desktop app credentials, download the JSON, run the guided CLI, authorize, save the token, add the env var, restart. Every OAuth-based integration (Outlook, Gmail, Spotify, GitHub) would require a similar ceremony with a different provider console.

The second problem: every MCP integration requires boilerplate wrapper code. **Smart Home no longer uses this pattern** — it now calls Home Assistant directly via `plugins/smart_home/ha_client.py`. The historical MCP-wrapper example below remains for Composio auto-bridged integrations.

The third problem: even if we solve definition and auth, loading 100+ tool descriptions into the system prompt will degrade LLM accuracy. Research shows ~23% accuracy degradation beyond 15 tools in context. The tool manifest must stay lean regardless of how many integrations are registered.

These are three **orthogonal** problems:

1. **MCP → CodeAct boilerplate** — hand-written wrapper plugins for every MCP server
2. **Auth setup latency** — the 4-hour ceremony in a provider console
3. **Context budget** — the system prompt can't hold 100+ tool signatures without degrading performance

---

## What Exists Today

### Integration Gate (Well-Designed)

The `IntegrationManager` pattern is sound: lazy-loading factories, refresh hooks, fail-safe registration, config validation. The architecture isn't the problem — the one-time setup ceremony is.

### Two Transport Patterns

| Transport | Example | Auth | Setup |
|---|---|---|---|
| **Direct HTTP** | Calendar, Smart Home | OAuth token file, or Smart Home panel / CredentialStore | Calendar: ~4 hours first time; Smart Home: in-app Connect (~2 min), or contributor `task setup:home` |
| **MCP stdio / HTTP** | Composio auto-bridged apps | Composio Connect Link | ~30 sec |

### MCP → CodeAct Bridge (Manual)

Historical note: Smart Home originally wrapped MCP tools as `@tool` functions. It now uses a bespoke HA client with eight curated tools (`refresh_home_assistant`, `organize_device`, plus the original setup/control set). Composio auto-bridge still generates thin wrappers from MCP schemas.

### Semantic Tool Router (Solves Problem 3)

The `ToolRouter` manages context budget using a **two-density manifest** with **plugin-level utterance routing**:

- **Namespace prefix (cached, every plugin):** One `jarvis.<plugin>: <description>` line per enabled plugin, plus explicit `@tool(manifest="full")` opt-ins. Turn-invariant, sits in the static half of the system prompt so providers can cache it.
- **Full-density tail (per-turn, routed plugins):** Signature + full docstring + return-schema hint for all mounted tools in matched plugins.
- **Mounted-tool discovery:** `jarvis.system.search_tools()` searches mounted `jarvis.*` tools that were not in the routed tail; `jarvis.composio.search_catalog()` remains the slower remote catalog fallback for unmounted Composio tools.

Routing is one scoring pass: each routable plugin owns a list of utterance vectors (hand-written or auto-generated by `utterance_cache`), and the user query is scored by **max-pool cosine** over those vectors. This preserves narrow intents that would otherwise be averaged away by a centroid (Tool2Vec research: utterance-based retrieval ~39% better recall than tool-description-based). Phase 8.5 dropped per-tool description embeddings — the signal-to-noise on MCP/Composio descriptions was poor and the tail bloat caused weak fast-path models to stall.

Both bespoke plugins and auto-bridged MCP plugins flow through the same routing path.

## Why CodeAct Is Already the Right Architecture

Anthropic shipped "Programmatic Tool Calling" in November 2025, calling it a breakthrough — presenting MCP tools as code APIs, generating typed function stubs that an agent calls from a sandbox. Their approach yields ~98.7% token reduction by keeping intermediate data in the sandbox and only returning final results to context.

This is architecturally identical to what JARV1S already does. The CodeAct executor mounts tools on `jarvis.<plugin>.<tool>()`, the agent writes Python that composes them, and intermediate results stay in the sandbox. The difference: Anthropic's system generates stubs from any MCP server dynamically. JARV1S requires a hand-written `JarvisPlugin` for each integration.

The missing piece is not a new paradigm — it's a **bridge** that turns MCP tool schemas into the Python callables CodeAct already expects.

## Industry Context

### The OAuth Problem

There are 70+ variations of OAuth 2.0 across providers. Each has different scope naming, token formats, refresh strategies, and error responses. The industry has converged on:

**Managed auth platforms** (Composio, Nango, Unified.to) — pre-registered OAuth apps. The user clicks a Connect Link, authorizes, done. No developer console. Composio provides managed OAuth apps for 500+ services. Free tier: 20,000 tool calls/month, no credit card.

**Self-hosted OAuth brokers** (Nango open-source) — free self-hosted edition handles OAuth for 500+ APIs. Only covers auth (no syncs or webhooks), which is all JARV1S needs. More operational overhead than Composio but keeps credentials on your infrastructure.

**Per-ecosystem reuse** — one OAuth app per provider ecosystem. A single Google Cloud project with added scopes covers Calendar, Gmail, Drive, etc. A single Azure AD app covers Outlook, OneDrive, Teams.

### The MCP Bridge Problem

The MCP ecosystem has exploded (10,000+ community servers). Every MCP server exposes tools via `tools/list` with JSON schemas. The gap: converting these schemas into CodeAct-callable functions. Libraries like `mcp-use` solve this for LangChain/OpenAI, but no standard bridge exists for CodeAct's Python-function-call paradigm.

## Design

### The Only Distinction That Matters

The real question is: **how much do you care about the LLM's behaviour with this tool?**

| Category | When | Examples |
|---|---|---|
| **Bespoke** | Integration is core, worth hand-crafted docstrings, VOICE policy, structured return types | Calendar, Smart Home, Email |
| **Auto-bridged** | Integration is convenience, auto-generated wrappers are good enough | Spotify, GitHub, Notion, Todoist |

Auth and transport are orthogonal — handled by the Integration Gate regardless of category. A bespoke plugin can use MCP (Smart Home), direct HTTP (Calendar), or Composio for auth. An auto-bridged plugin can use a local MCP server or a Composio-hosted one. These are independent choices.

```
┌───────────────────────────────────────────────────────────┐
│                    jarvis.* namespace                      │
│                                                           │
│  Bespoke Plugins               Auto-Bridged Plugins       │
│  ┌──────────────┐              ┌──────────────────┐       │
│  │ calendar     │              │ spotify          │       │
│  │ smart_home   │              │ github           │       │
│  │ email        │              │ notion           │       │
│  │ (hand-craft) │              │ (auto-generated) │       │
│  └──────┬───────┘              └────────┬─────────┘       │
│         │                               │                 │
│  Any transport:                  MCP Auto-Bridge           │
│  httpx, MCPClient,              (from any MCP server)     │
│  or anything else                       │                 │
│         │                               │                 │
│  Any auth:                       Any auth:                │
│  self-managed OAuth,             Composio managed,        │
│  API key, MCP token              API key, whatever        │
└───────────────────────────────────────────────────────────┘
```

### 1. MCP Auto-Bridge (Solves Problem 1)

A generic mechanism that takes any MCP connection and auto-generates CodeAct-callable tools from the MCP tool schemas. The generated functions must satisfy two contracts:

- **The executor contract:** real async Python functions callable as `await jarvis.x.y(arg=val)`
- **The scanner contract:** `inspect.signature(func)` returns typed parameter info; `func.__doc__` returns a useful description

**How it works:**

1. Read `mcp_servers.yaml` listing MCP servers to bridge (name, command/url, args, env, optional tool allowlist, optional utterances).
2. For each server, connect via `MCPClient` (stdio) or Streamable HTTP, call `tools/list`.
3. For each MCP tool, generate an async Python function:
   - Body: closure that calls `MCPClient.call_tool(name, kwargs)`.
   - Signature: build `inspect.Parameter` objects from the JSON Schema properties, set `func.__signature__` (Python's `inspect.signature()` checks this attribute first — no `exec()` or code generation needed).
   - Docstring: set `func.__doc__` from the MCP tool description.
4. Wrap each `MCPBridgePlugin` instance as a `JarvisPlugin` subclass and register it via `registry.register()` (see [Registry Integration](#registry-integration) below).

**Schema-to-signature mapping:**

| JSON Schema type | Python annotation | Notes |
|---|---|---|
| `string` | `str` | |
| `integer` | `int` | |
| `number` | `float` | |
| `boolean` | `bool` | |
| `array` | `list` | |
| `object` | `dict` | Nested objects stay as `dict` for auto-bridged; Pydantic models for promoted tools |

Required properties become positional-or-keyword parameters. Optional properties get `None` defaults. This is intentionally simple — edge cases (union types, nested schemas, `oneOf`) flatten to `dict` or `str`. Correctness over cleverness.

**Return value normalization:** The existing `MCPClient.call_tool()` already handles this: single `TextContent` → `str`, multi-content or mixed types → `list`. Auto-bridged tools inherit this behavior. The LLM receives either a string or a list of content dicts — simple enough to work with in CodeAct. No additional normalization layer needed.

**What this produces for full-density manifest entries:**

```
- jarvis.github: GitHub API tools
  * jarvis.github.create_issue(title: str, body: str, labels: list)
    """Create a new issue in a repository."""
  * jarvis.github.list_pull_requests(state: str, sort: str)
    """List pull requests for the repository."""
```

The scanner reads `__signature__` and `__doc__` — the same attributes it reads for bespoke tools. The stable prefix still shows only the plugin namespace unless a tool opts into `@tool(manifest="full")`; these full entries appear when the plugin is routed. The `@tool` decorator is **not required** for MCP bridge discovery: it exists for DI injection (`inject=["client"]`) and manifest metadata, while `get_tools()` is the enumeration mechanism and `get_visible_signature()` handles undecorated functions by filtering `self`. No scanner changes needed.

**Fail-safe startup:** If a configured MCP server fails to start (command not found, network unreachable, process crash), the bridge logs the failure, skips that server, and continues startup. Same pattern as the existing Integration Gate — a bad `mcp_servers.yaml` entry never takes down the system. Server availability is surfaced via `jarvis.system.get_status()`.

### Registry Integration

The `PluginRegistry` currently discovers plugins exclusively via filesystem scan of `plugins/`. Auto-bridged plugins are created at runtime — they don't exist as files in that directory.

**Solution:** Add `registry.register(plugin_instance)` — a programmatic registration path alongside filesystem discovery. The method adds the instance to `self.plugins` after validation. This is a one-method addition to the registry, not an architectural change.

**Load order and promotion priority:** `load_plugins()` (filesystem scan) runs first. `register()` calls from the auto-bridge run second. If a plugin name already exists in the registry (i.e., a bespoke plugin with the same name was found on disk), the auto-bridge skips it. **Bespoke always wins.** This makes promotion simple: write a bespoke plugin with the same name as the MCP server, drop it in `plugins/`, and the auto-bridged version is automatically shadowed. No config changes needed.

### 2. Context Budget via the Tool Router (Solves Problem 3)

Each auto-bridged MCP server registers with the `ToolRouter` via `register_plugin(name, tools_dict, utterances=utterances)`. Adding many servers doesn't change the stable-prefix shape much — the router scores all plugin candidates and promotes only the matched plugin namespaces into the full-detail tail.

**Utterances for auto-bridged servers:**

The `mcp_servers.yaml` config accepts optional `utterances` per server. If provided, these hand-written example queries are embedded as the plugin's utterance vectors. If not provided, `core/integrations/utterance_cache.py` synthesizes them from the plugin description + tool docstrings via one cached LLM pass. Hand-written utterances are cheaper and more accurate.

```yaml
servers:
  - name: github
    type: composio
    tools: [GITHUB_CREATE_ISSUE, GITHUB_LIST_ISSUES, ...]
    utterances:  # hand-curated — better routing accuracy
      - "GitHub issue"
      - "pull request"
      - "repository"
      - "code review"

  - name: some_tool
    type: composio
    tools: [SOME_TOOL_ACTION, ...]
    # no utterances — curated routing files or utterance_cache fallback supply them
```

**Allowlist (optional):** A `tools` allowlist restricts which tools are mounted from a server. If omitted, all fetched tools are mounted. Routing is plugin-level today: if the plugin matches, all mounted tools for that plugin are promoted to the tail.

The full-density tail token cost scales with how many *plugins* the active routing policy matches (voice default: max 3, budget-bounded) and how many tools those plugins mount. Large toolkits should use allowlists or bespoke wrappers for hot paths; otherwise a routed plugin can still add a large tail.

```yaml
  - name: slack
    type: composio
    tools:  # optional: curated subset of Slack's 147 tools
      - SLACK_SEND_MESSAGE
      - SLACK_FETCH_CONVERSATION_HISTORY
      - SLACK_SEARCH_MESSAGES
      # ... up to ~15 curated tools
```

### 3. Schema Caching

MCP `tools/list` is called on every connection. To avoid per-boot latency (especially with many servers):

- Cache `tools/list` results to disk as JSON with a 24-hour TTL.
- On boot, load from cache. Refresh in background if stale.
- Force refresh via `jarvis.system.refresh_integrations()`.
- Invalidate on config change (hash `mcp_servers.yaml` content).
- **Stale tool handling:** If the agent calls a cached tool that no longer exists on the server, `MCPClient.call_tool()` will return an error. On "tool not found" errors, the bridge invalidates the cache for that server and logs a warning. The error surfaces to the agent as a clear message, not an opaque failure.

### 4. Two-Tier Auth (Solves Problem 2)

**Tier 1 — Core integrations (Calendar, Email, Smart Home):** Privacy-sensitive, high-frequency, latency-critical. Self-managed with ecosystem OAuth consolidation:

```
task setup:google    # One-time: Calendar + Gmail + Drive scopes
task setup:microsoft # One-time: Calendar + Mail + OneDrive scopes
```

Each ecosystem setup is done once. New services within the ecosystem need a re-run of the setup script to authorize additional scopes (5–10 min re-authorization, not a fresh 4-hour ceremony).

**Tier 2 — Convenience integrations (Spotify, GitHub, Notion, etc.):** The long tail. Composio's free tier solves this:

```
User: "Connect my Spotify"
  → Jarvis sends Composio Connect Link
  → User clicks link, authorizes with Spotify (Composio's OAuth app)
  → Composio manages the token

User: "Play my Discover Weekly"
  → jarvis.spotify.play_playlist(name="Discover Weekly")
  → MCP Auto-Bridge → Composio API → Spotify API
```

**Composio integration is not plug-and-play.** Composio provides MCP server URLs and a Python SDK, but the integration requires:
- Create a Composio project and get an API key
- Manage connected accounts per `user_id` (JARV1S user → Composio user)
- Handle the Connect Link flow: generate link → user authorizes → Composio redirects to a callback URL with `status` and `connected_account_id` params. This is a standard OAuth redirect, not polling or webhooks.
- Provide a callback endpoint (`/api/v1/auth/composio/callback`) to receive the redirect
- Configure which Composio apps to expose

This requires a `ComposioGateway` adapter in `core/integrations/` — not just a config entry. The adapter manages user mapping, connection state, and exposes tools through the standard MCP Auto-Bridge. Uses Composio v3 REST API: auth configs (`ac_xxxx`) are created once per toolkit, and per-toolkit MCP server configs are created once and reused across users.

**Frontend work:** The Connect Link flow requires a `ConnectWidget` in the SDUI registry — a widget type that renders a clickable auth link and shows feedback when auth completes ("Spotify connected — tools now available"). The existing `WidgetRegistry` maps server-pushed intents to frontend components; `ConnectWidget` is a new entry. This is Phase 3 frontend scope.

**Disconnect flow:** `jarvis.system.disconnect_integration(name)` revokes the Composio connected account and removes the server's tools from the registry. Prevents orphaned connections.

**Free tier viability:** 20,000 calls/month, no credit card. A personal assistant making ~50 tool calls/day across all integrations uses ~1,500/month — well within the limit.

## What NOT to Build

| Approach | Why Skip |
|---|---|
| **Meta-tool / search-then-execute** | Breaks CodeAct. The LLM can't write `jarvis.spotify.play()` — it has to write `execute_tool("spotify_play", {...})`. Loses Python composition, the core differentiator. |
| **MCP-Zero / JIT tool loading** | Research-stage. Per-turn tool discovery adds latency. Overkill for a personal assistant's scale. |
| **MCP-aware CodeAct (dual invocation)** | Two paradigms (`jarvis.x.y()` and `mcp.call()`) confuses the LLM and doubles manifest format complexity. |
| **Full web OAuth framework** | Building `/auth/connect`, `/auth/callback`, provider configs, token encryption, and refresh handling for every provider is the 200–800 hours of work this proposal avoids. Use Composio for the long tail. Revisit for core integrations later if the CLI ceremony becomes untenable. |
| **FAISS/vector database** | In-memory dict + numpy cosine similarity is sufficient for the ~100-200 tool vectors in a personal assistant. No additional dependency needed. |

## Implementation

### Phase 1: MCP Auto-Bridge (stdio only)

Build the auto-bridge in `core/integrations/`. Scoped to stdio MCP servers only — remote/HTTP servers are Phase 1b.

- `MCPBridgePlugin` — `JarvisPlugin` subclass that generates tools from MCP schemas
- `registry.register()` — programmatic plugin registration path
- `mcp_servers.yaml` config format (name, command, env, optional tools allowlist, optional utterances)
- Schema-to-signature generation via `__signature__` override
- Schema caching (disk-based JSON, 24h TTL, invalidation on tool-not-found)
- Fail-safe startup (skip failed servers, log, continue)
- Synthetic utterance generation for the Tool Router
- Test with a local MCP server (e.g., filesystem or GitHub)

### Phase 1b: Streamable HTTP Transport

The existing `MCPClient` is a stdio transport — subprocess stdin/stdout with newline-delimited JSON-RPC. Streamable HTTP is a fundamentally different protocol: HTTP POST for client-to-server, optional SSE for server-to-client, connection lifecycle via HTTP semantics not process lifecycle. This is a second transport implementation, not an extension of the first.

Required before Phase 3 (Composio uses HTTP) and for any remote community MCP server.

- `StreamableHTTPClient` — same interface as `MCPClient` (`start`, `list_tools`, `call_tool`, `shutdown`) but over HTTP+SSE
- `mcp_servers.yaml` distinguishes transport: `command` → stdio, `url` → HTTP
- Shared `MCPTransport` protocol so the auto-bridge doesn't care which transport is underneath

### Phase 2: Ecosystem OAuth Consolidation

Extend `setup_calendar.py` → `setup_google.py`. Support multi-scope OAuth apps. Build `setup_microsoft.py` for the Microsoft ecosystem. Calendar multi-provider (existing proposal) uses this.

### Phase 3: Composio Gateway

- `ComposioGateway` adapter in `core/integrations/` — manages user mapping, connection state, Connect Link generation. Lazily creates auth configs and MCP server configs on Composio via v3 REST API; caches IDs in memory.
- `/api/v1/auth/composio/callback` endpoint for redirect-based connection completion
- `ConnectWidget` SDUI component — renders auth link, shows connection status feedback
- `jarvis.system.disconnect_integration(name)` tool for revoking connections
- `composio` type in `mcp_servers.yaml` for Composio-backed servers — **one entry per app**, not one monolithic server. `ComposioGateway` creates separate MCP endpoints per connected app, so each has its own namespace.
- **Hot-reload path:** When `/api/v1/auth/composio/callback` fires, the gateway discovers tools for the newly connected app via `POST /api/v3/mcp/servers/generate`, creates and registers the `MCPBridgePlugin` instance via `registry.register()`, mounts tools on the `jarvis` namespace, and triggers the `ToolRouter` to compute embeddings for the new plugin at runtime (not just at startup).
- Test end-to-end: "Connect my Spotify" → click → authorized → `jarvis.spotify.*` tools available immediately without restart

## Tradeoffs

**Composio dependency for convenience integrations:**
- Pro: eliminates hours of setup per integration, generous free tier
- Con: external dependency, API calls route through their servers, pricing can change
- Mitigation: only convenience integrations use Composio. Core integrations remain fully self-hosted. If Composio changes pricing, the MCP Auto-Bridge still works with any other MCP server — swap the backend, keep the tools.

**Auto-generated vs hand-crafted docstrings:**
- Auto-generated: functional but lack VOICE policy, Pydantic return types, and CodeAct-optimized guidance. The LLM will call these tools successfully but may use them less elegantly than bespoke tools.
- Hand-crafted: better LLM behavior but hours of work per integration.
- Compromise: auto-bridge with promotion path. Start auto-generated, promote to bespoke when a tool becomes important enough to justify the effort.

**Synthetic utterance quality:**
- Auto-generated utterances from tool names/descriptions are rough. The router may fail to activate the right MCP server for ambiguous queries.
- Mitigation: hand-curate utterances for the 5-10 most important auto-bridged servers. Let the rest use synthetic. Monitor routing accuracy and curate as needed.

---

## What This Does NOT Do

- **No replacement of bespoke plugins.** Calendar, Smart Home, and other core integrations keep their hand-crafted plugins with tuned docstrings.
- **No Composio for core integrations.** Privacy-sensitive services (calendar, email, smart home) use self-managed auth.
- **No MCP server hosting.** JARV1S consumes MCP servers, it doesn't become one.
- **No multi-user auth.** Personal assistant. One user, one set of credentials per service.
- **No meta-tool / search-then-execute pattern.** Tools are real Python functions in the `jarvis.*` namespace, callable directly by CodeAct.
