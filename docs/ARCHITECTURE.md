# JARV1S Architecture Overview

This document serves as a high-level guide to the JARV1S codebase for developers. The system is designed for **low-latency, stateful voice interaction** and **proactive external observation** using a layered monolithic architecture.

## 1. High-Level Layers

| Layer | Directory | Responsibility |
| :--- | :--- | :--- |
| **Delivery** | `backend/api/` | Handles network protocols (WebSockets, REST). No business logic here. |
| **Orchestration** | `backend/core/turns/` | `orchestrator.py` coordinates turn lifecycle (ingest → agent → persistence → trigger settlement); `history.py` owns conversation-window projection/loading; `execution.py` owns the delivery-agnostic agent loop; `delivery.py` owns per-turn presentation (WS fan-out, sentence buffering, TTS worker) behind a single-method `DeliveryStrategy` protocol. Channel-agnostic — voice, text, and headless (automation/prefetch/SystemPulse) turns all flow through here. |
| **Voice I/O** | `backend/core/voice/` | Audio workers consumed by the orchestrator: STT, TTS, VAD, wake word, model-based turn detection, and the per-session `SpeechProcessor` state machine. Voice-specific implementation detail behind the orchestration layer. |
| **Logic** | `backend/core/` | Brains of the system: LLM reasoning, persona management, and tool execution. |
| **Infrastructure** | `backend/services/` | Cross-cutting concerns: Event Bus, Database, Cache, and Performance monitoring. |
| **Frontend** | `frontend/src/` | Low-level audio capture (16kHz), playback (PCM streaming), and UI. |
| **Satellite** | `satellite/` | Thin Pi voice endpoint: mic/speaker I/O, presence handshake, WebSocket transport, optional on-device PASSIVE `edge_wakeword`. No on-device STT, TTS, or agent. See [SATELLITE.md](./SATELLITE.md). |

`task start` runs JARV1S as a local **Jarvis Host**: MongoDB is bound to localhost, the backend serves the built React app from `/`, and first-run setup gates WebSocket chat until an LLM provider key has been validated and the core text runtime is initialized. Future clients pair to this Jarvis Host; they do not receive provider API keys.

### Host Launch Surfaces

Jarvis can be opened through multiple launch surfaces that share the same startup contract ([`docs/deployment/JARVIS_HOST_STARTUP_CONTRACT.md`](../deployment/JARVIS_HOST_STARTUP_CONTRACT.md)) and readiness APIs:

| Surface | Audience | Responsibility |
| :--- | :--- | :--- |
| `task start` | Contributors | Lockfile installs, Docker services, frontend build, backend app mode |
| Packaged desktop app (`apps/desktop`) | Phase 1b technical beta | Tauri shell supervises bundled `mongod` and app-owned Python backend (Docker only when `JARVIS_SERVICE_PROVIDER=docker`); see [JARVIS_HOST_APP.md](./proposals/JARVIS_HOST_APP.md) |
| Paired browser / satellite | Presence clients | Connect to an already-running Host; no process management |

The desktop shell owns **process supervision, startup UX, release metadata, updater checks, and support export**. FastAPI remains the Jarvis Host: `/api/v1/health`, `/api/v1/version`, and `/api/v1/setup/state` stay authoritative for reachability and setup readiness. The React app inside the WebView uses the same REST/WebSocket contracts as browser clients.

### Client lifecycle contract

| Runtime | Process owner | Voice endpoint lifetime | Liveness |
| :--- | :--- | :--- | :--- |
| Desktop Host | Tauri supervisor | Backend/services continue while the window is hidden; the WebView mic remains a best-effort client surface | Tauri launch state is Host truth; Uvicorn protocol ping/pong owns hidden-socket liveness |
| Browser / phone | Browser or installed web app | Best effort while the page process is alive | Visible client heartbeat detects dead intermediaries; resume performs an immediate probe/reconnect |
| Satellite | Service manager on the satellite | Always-on room endpoint | Satellite reconnect loop + application heartbeat |

### Always-listen surface contracts

“Accessible anytime in the house” means a **live satellite** (continuous stream today; on-device PASSIVE edge wake when enabled), not a backgrounded WebView or phone tab.

| Surface | Always-listen | Role |
| :--- | :--- | :--- |
| **Satellite** | Yes | Room ears/mouth — wake and speak without touching the Mac |
| **Desktop (WebView)** | No — focused best-effort | Host UI + interactive voice while the window can capture; focus resumes capture and surfaces `Mic stalled` when PCM is dead |
| **Phone / browser** | No | Companion — PTT, text, or short interactive capture |

Desktop work is honesty + resume only: no native Tauri mic and no wakeword in JS. Playback keep-alive (`runtime/audioSessionKeepAlive`) is independent of capture mute. Proactive `deliver_to` still resolves to live speaker presence; muting the desktop mic does not disable satellite delivery.

The WebView and browser stop their JavaScript heartbeat timers while hidden so throttled timers cannot close healthy sockets. Uvicorn is pinned to the `websockets` implementation and sends protocol ping frames independently of JavaScript. On foreground/focus/network resume, the client probes immediately, resumes the capture `AudioContext`, reacquires the mic when tracks ended or PCM stalled, and rebuilds runtime state from `system.connect` plus the widget snapshot. This does not make a WebView an always-on endpoint across app quit or system sleep; satellites remain the always-on room surface.

**Desktop playback session:** The packaged Tauri Host mounts a process-lifetime silent HTMLAudio keep-alive (`frontend/src/runtime/audioSessionKeepAlive.ts`) so macOS WKWebView does not tear down CoreAudio after prolonged background/idle. Without it, TTS can report `playback_summary` `render_completed` with a `running` AudioContext while no sound reaches the speakers. The keep-alive is App-owned and independent of mic mute/stop so proactive speaker delivery remains valid when capture is disabled.

## 2. The Turn Pipeline

All interaction flows through `AssistantOrchestrator.process_turn()`, which is a thin caller over layered turn modules:

- `process_turn()` — **ingest + lifecycle**: session lookup, STT / text / `system_context` routing, turn-lock acquisition, voice-mode transitions, `VOICE_TURN_END` publish, and trace persistence via `_persist_trace()`.
- `execute_turn()` (`backend/core/turns/execution.py`) — **delivery-agnostic agent loop**: loads history via `history.py`, builds context, routes tools, iterates `JarvisAgent.process_stream`, and forwards each yield as a `StreamEvent` to a `DeliveryStrategy`. Mutates a caller-owned `TurnResult` so partial state survives `CancelledError`. The orchestrator keeps a thin `_execute_turn()` wrapper for call sites.
- `DeliveryStrategy` (`backend/core/turns/delivery.py`) — single `on_stream(event)` method. `VoiceDelivery` handles sentence splitting, the speech gate, WS fan-out, and the TTS worker; `HeadlessDelivery` is a no-op for silent automations, prefetch, and SystemPulse escalations (Phase 9a+).
- Trigger due-events dispatch through named `act` / `offer` / `tell` paths on the orchestrator; announce and offer/evaluate outcomes settle through one `_settle_trigger_instance()` method that still calls `TriggerService` transition APIs.

Three input modalities converge here:

| Modality | Trigger | STT | TTS |
| :--- | :--- | :--- | :--- |
| **Voice** | Wake word + VAD endpoint accepted by `TurnDetector` | Yes | Yes |
| **Text** | `user_text` WS message | Skipped | No |
| **System** | Event bus (alerts, protocols, automations) | Skipped | Yes |

**Turn vocabulary:**

| Name | Scope |
| :--- | :--- |
| `VoiceInputTurn` | Voice input capture state for one logical user utterance: VAD/STT transcript, endpoint metadata, and late continuation. It is not an assistant execution or delivery attempt. |
| `accepted_input_task` | Voice-only post-commit handoff task. Active between endpointing commit and assistant run start: runs streaming STT finalize, local-command check, and schedules `process_turn()`. Fast recovery **awaits** this task to finish input finalization (PCM is already consumed — cancelling mid-handoff drops segment text); then cancels `current_run_task` if the assistant run started. Cleared by `_resolve_endpoint_candidate`'s finally block. |
| `current_run_task` | The active assistant execution/delivery task. Set by `_commit_voice_turn` (voice), `handle_text_input` (text), and trigger/protocol/prefetch paths. Barge-in and interruption cancel this. Cleared in `process_turn()`'s finally block. |
| `AssistantOrchestrator.process_turn()` | One accepted user/system input execution: context build, agent loop, delivery, trace persistence, and lifecycle cleanup. |
| `VoiceDelivery` / `HeadlessDelivery` | One output delivery attempt for a run. Delivery owns TTS/audio cancellation; it does not own voice input state. |
| `turn_id` | Correlation id shared across input, execution, delivery, `conversations`, `turn_runs`, and protocol logs. |

**Attachments** are buffered, not turn-creating. `user_attachment` WS messages append to `session.pending_attachments`; `_drain_attachments()` consumes them at the next turn boundary and merges text + images into OpenAI-format content parts for the LLM. Attachment turns set the agent context modality to `multimodal` and use the `text_default` tool-routing policy.

**Voice detection flow:**
1.  **Ingestion**: Browser or satellite client streams 16kHz mono PCM chunks over WebSocket (`user_audio`). Satellites use the same contract; see [SATELLITE.md](./SATELLITE.md).
2.  **Wake Word**: In `PASSIVE` mode, `SpeechProcessor` buffers ~3s. `WakeWordService` runs a two-stage cascade: Stage 1 (finetuned **Jarvis.onnx** on frozen embeddings) proposes candidates; Stage 2b is a thin wake adapter over the session-scoped `EnrolledSpeakerVerifier` (process-shared TitaNet-small extractor vs the owner embedding gallery under `DATA_DIR`, mean-cosine scored). Profiles are bound to the model artifact SHA-256, so model changes require re-enrollment rather than silently reusing incompatible embeddings. Until enrollment, Stage 2b is accept-all. The same verifier scores barge-in candidates during `ACTIVE_AI_TURN` with age-gated mismatch (short endpoints wait until max-wait; at most one rescore). Wake-prefix and exact emergency controls are intentionally public pre-commits.
3.  **VAD**: Upon wake, transitions to `ACTIVE_IDLE` — TEN VAD detects speech start and proposes endpoint candidates. While the AI is speaking or processing, mode is `ACTIVE_AI_TURN` (barge-in threshold raised; enrolled-owner speaker gate before commit).
**STT backends** are selected by host-level voice runtime config (`system_config.voice_config`) and managed in the app under **Settings → Voice & Audio**. Provider changes apply to the next voice turn without a backend restart.

| Backend | When text appears | Commit-time work | Fast recovery (user resumes within `fast_recovery_window`) |
| :--- | :--- | :--- | :--- |
| `cartesia` | Live `conversation.partial` from Cartesia (`ink-whisper` on `/stt/websocket` by default) | `StreamingSTTCoordinator.finish()` sends `finalize` and merges finals | Await `accepted_input_task` if still finalizing; cancel `current_run_task`; `continuation_prefix` + stream partials (reuses open stream when fast recovery fires before `finish`) |
| `apple_speech` | Live `conversation.partial` from Apple Speech helper (`apps/desktop/apple-stt-helper/`) | Same coordinator; helper waits for terminal `done` after `finalize` | Same handoff as Cartesia |

`process_turn()` receives `text=` after the WebSocket layer has finalized the active STT stream. If streaming produced no transcript, the turn is dropped — no batch MLX fallback on the voice path.

**Cartesia STT** uses `ink-whisper` on `/stt/websocket`. JARV1S VAD + audio EOU decide when to commit; then the client sends `finalize`. This is a product choice rather than environment configuration because it is more reliable for short commands.

**On-device streaming:** [research/LOCAL_STREAMING_STT.md](./research/LOCAL_STREAMING_STT.md) — one WebSocket per utterance to the Apple Speech helper; only `done` is terminal; audio EOU plus `apple_speech_commit_stability_delay` / `apple_speech_endpoint_max_delay`.

**Provider lifecycle and warming:**
- LLM activation validates the candidate, persists it, reinitializes the shared
  `LLMService`, and restores the previous config if initialization fails. The managed
  Ollama sidecar is controlled independently by the desktop host preference. Its model
  stays resident with `OLLAMA_KEEP_ALIVE=-1` while selected, then is explicitly unloaded
  after a successful switch to another provider; the lightweight sidecar remains ready.
- STT changes apply at the next turn boundary. Cartesia and Apple Speech use
  short-lived per-utterance WebSockets; the supervised Apple helper remains running
  while the Host is running, even when Cartesia is selected.
- TTS promotes an initialized candidate and defers closing the previous backend until
  active audio streams drain. Selected TTS is prewarmed after runtime startup and again
  on wake; Cartesia reconnects stale WebSockets and warms its voice model, while local
  Kokoro warms the selected voice through its helper.
- The desktop supervisor starts Apple Speech and Kokoro helpers independently of the
  selected provider. This favors fast switching and fault isolation over minimum idle
  memory; Ollama is the only materially heavy optional runtime and has a separate
  enable/disable lifecycle.

4.  **Endpointing**: `SpeechProcessor` owns the audio turn phase (`IDLE` / `SPEAKING` / `ENDPOINT_CANDIDATE`) and emits each VAD endpoint as a single edge. A VAD endpoint starts a session-owned `endpoint_decision_task`; the WebSocket loop keeps ingesting PCM into the same `StreamingSTTCoordinator` and the session's audio turn-detector stream while the task waits for `turn_detector_min_delay` and current transcript text. LiveKit local audio EOU (`v1-mini`) is the primary commit signal. If the detector says not done, the processor continues the same audio turn; if done or max-delay expires, the endpoint task consumes the buffer, registers itself as `accepted_input_task`, finalizes the active STT stream, runs local commands, then **turn admission** (`core/voice/turn_admission.py`) before scheduling `process_turn()` into `current_run_task`. Wake / barge-in / push-to-talk stamp `admission_source` earlier and are reused; ordinary `ACTIVE_IDLE` follow-ups are fail-open until a future DDSD producer sets `Directedness`. Barge-in admission during `ACTIVE_AI_TURN` remains enforced (owner speaker + public controls) and is separate from the endpoint handoff: stopping the assistant (`VOICE_USER_START`) does not finalize the user turn by itself. When a candidate commits while already `ENDPOINT_CANDIDATE` (including deferred soft-wait / endpointed max-wait), the resolver publishes `VOICE_USER_END` and schedules exactly one endpoint decision through the same helper as normal VAD endpoints; push-to-talk keeps its direct `_commit_voice_turn` path. Before scheduling `process_turn()`, the WebSocket layer checks exact local voice controls in `core/voice/local_commands.py` (`mute`, `power down`, `power on`, `stop listening`, etc.). Handled local commands mutate live session/audio state and, for attention controls, fast-path through the attention plugin/service; they never enter the LLM, tool router, or history path. Fast recovery remains only for late continuations after a turn has crossed the commit point.

**Common tail (all modalities):**
1.  **Turn Lock** prevents concurrent generation.
2.  **Tool Routing** — ToolRouter scores each enabled, routable plugin by max-pool cosine over its utterance vectors (hand-written, curated, or generated-cache fallback). Matched plugins plus an explicit always-on FQN set become the per-iteration `tools=` payload; ToolRouter budgets against JSON-schema tokens, not prompt prose. Simple turns keep the tight semantic cap; compound turns are split on cheap task boundaries and can promote more plugins only while the schema set stays under budget. Voice user turns use `voice_default`; text/multimodal turns use `text_default`; trigger system/headless turns use `system_hint` over a bounded combination of action message, instructions, and protocol context; that policy disables session carryover. Continuity has two sources: successful tool outputs retain the latest plugin set as tool focus, while successfully delivered live proactive turns retain their already-routed plugins for one user route (live connection handoff, restored from conversation `routed_tools` after a same-node reconnect). Neither path stores tool output, object ids, or prompt provenance; classifies the reply; or forces a call. The agent interprets conversation history plus optional `reply_grounding` on the unsettled proactive assistant turn; destructive/context-bound tools still validate identifiers. `reply_grounding`, source events, and rendered assistant text are not embedded for routing. See [Tool Routing Architecture](./proposals/built/DYNAMIC_TOOL_ROUTING.md).
3.  **Agent** executes the **structured capability-call loop** on the configured assistant model for every direct turn (voice, text, system, and headless). Depth that needs a stronger model uses explicit `agents.dispatch()`.
4.  **TTS** (voice/system only) streams sentences to Cartesia as they are generated. During multi-tool chains, intermediate text is speech-gated — only the opening acknowledgement and final response are spoken. An early flush fires at the nearest clause boundary if 800ms + 60 characters have accumulated without a sentence break (first sentence only).
5.  **Delivery**: Voice turns push audio for gapless `AudioContext` playback. Text turns send `conversation.response` only. Assistant text events carry `turn_id` for whole-turn client correlation and `response_id` for the current streaming segment.
6.  **Sync**: `audio.tts_end` marks backend TTS producer completion; `audio.playback_end` from the playback client (browser or satellite) echoes `turn_id`, marks actual speaker drain, and resets the Activity Timeout (30s) only for the matching audio turn.

## 3. Key Directory Responsibilities

### `backend/api/routes/`
- **`integrations.py`**: REST endpoints for integration lifecycle (list, connect-link, disconnect, reconcile). Thin — delegates to `lifecycle/`.
- **`auth.py`**: OAuth callback and credential management for two flows:
    - **Composio**: Redirect endpoint after user authorization; reconciles via `lifecycle/` and posts result back to the frontend popup via `postMessage`.
    - **Bespoke OAuth** (Google + Microsoft): configure/authorize/callback/status/delete endpoints. Google uses a popup authorization-code flow; Microsoft uses MSAL device-code. Credentials persisted via `AuthManager`, CSRF-protected via short-lived nonces. Frontend counterpart: `OAuthWidget` — a phase-driven SDUI component (`needs_config` → `needs_auth` → `connected`).
- **`webhooks.py`**: Composio webhook ingestion. Verifies signatures (Standard Webhooks protocol), handles connection lifecycle events (e.g., `connected_account.expired` → local teardown), and normalizes V3 trigger payloads for the automation engine.
- **`tasks.py`**: REST endpoints for background task listing and retrieval (`GET /tasks/`, `GET /tasks/{task_id}`). Typed Pydantic response models for `TaskSummary` and `TaskDetail`.
- **`base.py`**: Root health/version endpoints. `GET /health` reports setup-aware service readiness and returns HTTP 503 when the database is down so launchers and watchdogs fail closed; `needs_setup` / LLM-only `degraded` stay HTTP 200. `GET /version` exposes support metadata for the Jarvis Host app version and pinned runtime dependencies. Desktop launchers should consume these endpoints rather than duplicating readiness logic.
- **`setup.py`**: Jarvis Host setup/readiness endpoints. `GET /setup/state` reports readiness and `capability_lanes`; `POST /setup/llm/test` validates provider credentials; `POST /setup/llm/activate` atomically validates, persists, initializes, and rolls back provider config plus credentials on failure. Managed-local status/install/remove/activate endpoints live under `/setup/llm/local/managed`; `POST /setup/runtime/initialize` remains for startup recovery.
- **`smart_home.py`**: Smart Home overlay API. `GET /smart-home/status` delegates to `plugins/smart_home/ui_status.py` for explicit frontend states and a token-free `ha_url` plus controllable device summaries grouped by HA area. `GET /smart-home/discover` probes fixed local candidates concurrently. `POST /smart-home/auth/authorize` starts a Home Assistant IndieAuth browser flow; `GET /smart-home/auth/callback` exchanges the code, mints a named JARV1S long-lived token, persists `ha_config.url` + `HA_TOKEN`, revokes the temporary refresh token, and publishes the standard `auth.oauth.changed` event. `POST /smart-home/connect` remains the manual URL + long-lived-token path. `DELETE /smart-home/connect` clears product config. Shared callback HTML/event helpers live in `api/oauth_support.py`. Contributor CLI (`task setup:home`) reuses discovery and still owns Docker bootstrap; `.env` is a dev fallback only.
- **`device_auth.py`**: Per-device WebSocket auth for remote endpoints. Pairing codes for browsers/phones, `POST /device-auth/satellites` to mint a one-time room-speaker token + canonical `backend_ws_url`, and `POST /device-auth/ws-ticket` for short-lived connect tickets. Owner-auth is required for mint/issue paths. The packaged Host is the local trust root: direct loopback requests bypass pairing, are classified server-side as `desktop`, and still undergo WebSocket origin validation.
- **`presence.py`**: `GET /presence/` for the Rooms & devices overlay. Thin — delegates to `core/presence/service.py`, which merges live `ConnectionManager` sessions with provisioned `ws_device_credentials` into online/offline/revoked node rows (kind, room, capabilities, last seen, active node). Assign-room and `POST /presence/devices/{device_id}/revoke` update durable credentials and force-disconnect live sessions.
- **`preferences.py`**: `GET/PATCH /preferences/` for owner-scoped runtime preferences. V1 stores `audio.tool_cues_enabled` in MongoDB and broadcasts `preferences.update` to connected nodes after changes so browsers and satellites share one source of truth.
- **`history.py`**: `GET /history/` endpoint returning recent conversation turns as typed frontend transcript items. Includes `user` and `system` sources, but only `role="assistant"` delivered rows from system turns — raw `role="system"` execution-prompt rows (`SYSTEM EVENT / INSTRUCTION`) are filtered here as they are audit data, not user-facing conversation. Structured capability calls are projected from metadata (`capability`, `arguments`, `call_id`); tool outputs fold into the matching item. Provider reasoning rows (`metadata.turn_type="reasoning"`) project as `type="reasoning"` with `response_id` for transcript correlation. Silent/suppressed turns stay in the `GET /history/headless` audit feed only.

### `backend/api/websockets/`
- **`handlers.py`**: The entry point. Translates WebSocket messages into service calls. Keep this thin.
- **`presence.py`**: Defines the live presence identity contract at the WebSocket boundary. `connection_id` is the transport socket, `owner_id` is the trusted account/storage namespace, `node_id` is the mic/speaker/display endpoint, and `device_kind` is the endpoint class (`browser` | `desktop` | `phone` | `satellite`). Remote endpoints source kind and optional `location_ref` from their durable credential; the packaged Host kind is classified server-side as `desktop` on the trusted loopback path. Pairing may send a one-shot `client_surface` hint to set credential kind. Per-turn `speaker_id` is not presence identity: it is stamped on verified barge-in turns today and remains the seam for later household speaker tagging.
- **`connection.py`**: Manages live `Session` objects keyed by `connection_id`. Each connected node owns its own `SpeechProcessor`, voice-turn state, session-local `soft_muted` gate, owner preference snapshot, subscriptions, delivery state, and shared `EnrolledSpeakerVerifier`. Owner/node lookup maps exist only for compatibility and default delivery; new multi-room delivery should target an explicit connection or node. `update_node_location()` refreshes live `location_ref` on connected sessions after a bind. `system.connect` includes the owner’s persisted attention snapshot (`attention`) and runtime preferences (`preferences`); changes fan out to connected nodes (e.g., `status.update` with `attention`, `preferences.update`) so browsers and satellites stay aligned with Mongo-backed state after reload.

### `backend/core/`
- **`turns/`**: Turn lifecycle + delivery — channel-agnostic.
    - **`orchestrator.py`**: `AssistantOrchestrator` — owns turn-lifecycle concerns (session lookup, ingest, turn-lock, mode transitions, event-bus handlers, trigger due-dispatch, post-execution trigger settlement, and trace persistence). `process_turn()` is the thin caller; it upserts accepted user input as a pending row before execution, then delegates the agent loop to `execution.execute_turn()`. Named `_dispatch_act_trigger` / `_dispatch_offer_trigger` / `_dispatch_tell_trigger` paths keep due-decision, endpoint routing, protocol/prefetch, and task scheduling order. Owns a `self.headless_pool = HeadlessTurnPool(max_concurrent=settings.AGENT_HEADLESS_CONCURRENCY)` (default 2) for bounding concurrent headless callers.
    - **`history.py`**: `HistoryPolicy`, `LoadedTurnHistory`, and `load_turn_history()` — conversation-window projection for the agent. User turns use two-tier loading: full user-source budget (limit 200) plus a small sanitized system tail (limit 5). Short-term prompt history is scoped to `owner_id + origin node_id` and bounded by `CONVERSATION_SESSION_INACTIVITY_MINUTES`, where recent user turns and visible proactive deliveries (`announce`, `evaluate`, `prefetched`) keep the window alive; older turns stay durable and owner-wide searchable through `recall()`, but are not injected automatically after an inactivity gap. The user-source query excludes the current `turn_id` because the live input is appended separately by the agent loop. The system tail drops raw execution prompts and tool artifacts, then merges delivered assistant rows chronologically. If the newest settled proactive row has `reply_grounding` and no later user row, its scalar frame is projected for exactly the current reply and its persisted `routed_tools` restore route carryover after a same-node reconnect. Conversation sources are `user` | `system`; automation identity lives in origin metadata.
    - **`execution.py`**: `execute_turn()` — delivery-agnostic agent loop that builds history + context (including shared `build_turn_time_context()`), resolves tool routing / prompt mode, iterates `JarvisAgent.process_stream`, and forwards `StreamEvent`s to a `DeliveryStrategy` while mutating a caller-owned `TurnResult` in place.
    - **`reasoning_effort.py`**: `resolve_reasoning_effort()` — latency-contract gate for provider `reasoning_effort` (`None` on audio-bound turns; configurable low/medium/high for text/headless when the active `LLMService` reports `supports_reasoning_effort`). Orthogonal to delivery mode; applied per turn after tool routing.
    - **`delivery.py`**: `StreamEvent` (frozen, slotted, tag union incl. `reasoning`), `DeliveryStrategy` Protocol (single `on_stream`), `TurnResult` dataclass (caller-owned, mutated in place; `full_response` is model text only, `runtime_error` is harness/provider failure), `VoiceDelivery` (session-coupled: WS fan-out, sentence buffer, speech gate, TTS worker; forwards `conversation.reasoning` on text turns only; sole writer of `session.tts_sentence_queue` / `session.first_audio_sent` / `session.active_audio_turn_id`), and `HeadlessDelivery` (no-op for user-facing output; reasoning still captured in `turn_trace`). `perf.end("response_latency")` and `perf.end("turn_latency")` close inside `VoiceDelivery._tts_worker` on first audio; `response_latency` starts at accepted endpoint submission for user-facing latency, while `turn_latency` spans the whole voice turn for backend tracing. Only the first spoken sentence records `tts_first_chunk` (**Voice start**); later sentences use `tts_sentence` (diagnostics). Compact stage summaries are persisted to `turn_runs`; user-visible content stays in `conversations`.
- **`voice/`**: Audio I/O workers consumed by `VoiceDelivery` and by the per-session `SpeechProcessor`.
    - **`stt_service.py` / `tts_service.py`**: Pluggable STT/TTS behind `SwitchableSTTBackend` / `SwitchableTTSBackend`. **Cartesia** uses product-selected models (`ink-whisper` STT and `sonic-3.5` TTS). **`apple_speech`** uses the supervised Speech helper. **Local TTS** uses supervised Kokoro (`LocalTTSService` → `kokoro_tts_server.py`, `pcm_f32le` @ 24 kHz). Spoken replies also support `off` (text only). **`MLXSTTService`** is batch-only (`eval_stt.py`), not live voice.
    - **`streaming_stt.py`**: Per-turn `StreamingSTTCoordinator` when `stt_streaming_enabled` and the active backend exposes a session. Owns stream lifecycle, buffered-audio chunking, partial throttling (`conversation.partial`), and finalize timing for both Cartesia and Apple Speech.
    - **`local_commands.py`**: Pure local transcript classifier for exact room-control phrases. It normalizes capitalization/punctuation, strips a narrow wake-word prefix when present, and returns a `LocalVoiceCommand` enum. It does not inspect session state, route tools, or match substrings.
    - **`turn_admission.py`**: Pre-agent commit/suppress policy. `decide_barge_in_admission` enforces barge-in (speaker + public controls); `decide_followup_admission` routes `ACTIVE_IDLE` fail-open until a DDSD producer sets `Directedness`. Identity and addressivity stay separate.
    - **`turn_detector.py`**: Per-session `AudioTurnDetectorSession` wrapping LiveKit's local audio `TurnDetector` (`v1-mini`). Loaded lazily on first PCM; prediction failure falls back to VAD commit.
    - **`vad_service.py`**: TEN VAD for speech-boundary detection.
    - **`processor.py`**: Per-session `SpeechProcessor` — owns `VoiceMode` (PASSIVE / ACTIVE_IDLE / ACTIVE_AI_TURN), `SpeechTurnPhase` (IDLE / SPEAKING / ENDPOINT_CANDIDATE), wake-word circular buffer (`wake_preroll_seconds`, default 3s), VAD frame counting, endpoint edge/resume emission, and turn-buffer assembly. Wake-word and VAD turn starts both seed `turn_buffer` from the same rolling pre-roll so utterance onsets are not clipped. `add_audio(..., retain_preroll=...)` skips the rolling buffer while `session.soft_muted` so muted sessions do not seed turns with ambient conversation. Endpoint candidates are edge-triggered here so async STT/model finalization cannot double-submit a turn, but `ENDPOINT_CANDIDATE` still buffers audio and can resume the same turn when VAD sees speech return.
    - **`wakeword_service.py`**: Orchestrates the wake cascade in `backend/core/voice/wakeword/`: openWakeWord **Jarvis.onnx** as Stage 1 candidate detector, then Stage 2b as a thin adapter over the session-scoped `EnrolledSpeakerVerifier` (`backend/core/voice/speaker_verifier.py`) when an owner profile exists under `{DATA_DIR}/voice/speaker-profiles/`. Clean installs use `AcceptAllWakeVerifier` until first-run or Settings → Voice & Audio enrollment. The same verifier scores barge-in candidates (age-gated mismatch until max-wait; optional one rescore). Runtime false-trigger control is config-driven: `wakeword_sensitivity` (default **0.70**), `wakeword_patience` (default **3** consecutive 80ms frames above threshold — sustain filter implemented here, not via OWW's built-in `patience`), `wakeword_vad_threshold` (default **0.5** Silero VAD gate inside openWakeWord; degrades to sustain-only if the VAD model is unavailable at startup), `wakeword_speaker_threshold` (default **0.21**), and `barge_in_speaker_threshold` (default **0.21**, calibrated separately). See [WAKEWORD_ARCHITECTURE.md](./proposals/WAKEWORD_ARCHITECTURE.md).
- **`llm/`**: Provider boundary for all model calls.
    - **`service.py`**: `LLMService` facade — message assembly, first-token/idle timeout policy, retry on transient provider errors, delegates to a pluggable adapter. Exposes `supports_reasoning_effort` from the adapter.
    - **`adapters/litellm.py`**: `LiteLLMAdapter` — calls `litellm.acompletion`, streams provider-neutral `ModelEvent`s (`text`, `reasoning`, complete `tool_calls` assembled from OpenAI-style deltas), and detects reasoning-effort capability via LiteLLM model metadata.
    - **`types.py`**: `ModelEvent`, `ToolCallEvent`, `LLMStreamEvent`, and stream callback types shared by agent + perf layers.
    - **`providers.py`**: Preset base URLs/models and provider-specific request policies (e.g. Gemma `reasoning_effort=none` via `extra_body`).
- **`agent/`**: The core reasoning engine.
    - **`agent.py`**: `JarvisAgent` — streams model events, dispatches `CapabilityCall`s from provider `tools=` results, and continues until final text. Provider reasoning deltas surface as `AgentEventType.REASONING` (text clients only; never spoken on audio-bound turns). Harness and provider failures surface as `AgentEventType.ERROR`, not model `TEXT`. `tools=` is omitted when the configured model is chat-only (`action_capable` is false).
    - **`sdk.py`**: Claude Agent SDK subprocess helper used by `dispatch(mode="code")`.
- **`integrations/`**: The "Integration Gate". Centralizes credential management and client initialization.
    - **`manager.py`**: A lazy-loading service container. Handles async client creation on demand. Integrations register with `provider=` and `required_scopes=` to opt into `AuthManager` scope validation — the validated `OAuthToken` is injected into `config["_oauth_token"]` before the factory runs. Supports optional `refresh` callbacks for transparent token renewal.
    - **`mcp/`**: MCP transport layer and auto-bridge. `client.py` — stdio transport (subprocess + JSON-RPC). `http_client.py` — the current Streamable HTTP client (POST + SSE, including legacy `Mcp-Session-Id` support); stateless MCP is the preferred future remote boundary, but is not yet the implemented transport contract. `bridge.py` — auto-generates thin `JarvisPlugin` wrappers from any MCP server's `tools/list` schema so they share the same capability catalog as first-party plugins. `MCPBridgePlugin` is a thin wrapper: `get_tools()` returns all mounted tools. The per-turn `tools=` set and routing are handled centrally by `ToolRouter` (plugin-level utterance vectors). `config.py` — YAML config loader. `cache.py` — on-disk schema cache (24h TTL).
    - **`composio_gateway.py`**: Low-level Composio API client — Connect Link generation, connected-account queries, webhook subscription management, and per-app MCP tool registration.
    - **`lifecycle/`**: Central orchestration for integration management, split into submodules: `composio.py` (reconcile/connect/disconnect for Composio-backed integrations), `bespoke.py` (non-Composio MCP bridge teardown and local plugin refresh), and `_shared.py` (cross-module types, errors, and `is_toggleable()`). All connect/disconnect/reconcile/teardown flows route through here so the REST API, voice tools, OAuth callbacks, and webhook handlers share one code path. Derives authoritative connection state from remote Composio, detects local/remote drift, and coordinates plugin registry + ToolRouter updates. `is_toggleable()` — the source of truth for what the Tools UI exposes.
- **`auth/`**: Central OAuth credential lifecycle for bespoke (non-Composio) integrations. `AuthManager` singleton persists app credentials (`oauth_provider_configs`) and tokens (`oauth_tokens`) in MongoDB with in-memory caching; proactively refreshes before expiry; `ensure_scopes()` validates required scopes before any client factory runs, raising `ScopeGapError` on a gap. `ProviderConfig` and `OAuthToken` are separate Pydantic models — rotating the OAuth app never touches token records.
- **`setup/`**: Jarvis Host setup state and runtime readiness. `ResolvedLlmConfig` resolves from persisted `system_config.llm_config` plus `CredentialStore`; `compute_capability_lanes()` reports per-capability setup status. `JarvisRuntime` initializes the LLM-backed text runtime idempotently via `POST /setup/runtime/initialize` (and atomically via `POST /setup/llm/activate`). After initialize, `probe_action_capability()` runs a live tool-call/result round trip and persists `action_capable`; static LiteLLM function-calling metadata is not a gate. Models that fail the probe stay chat-only and `tools=` is omitted. Startup re-probes whenever `action_capable` is not already `True`. `readiness.require_llm_ready()` is the authoritative gate for user, voice, and headless/proactive turns. On the desktop Host, `managed_local_llm` provisions one isolated Ollama sidecar (`127.0.0.1:11435`) and one managed baseline model without touching user-installed Ollama on `:11434`. The Rust Host exclusively owns executable lifecycle; backend managed-model endpoints require that sidecar to be running.
- **`credentials/`**: Host-only bootstrap credential storage. Product-path LLM and Cartesia keys resolve from stored secrets (keyring or encrypted file). `get_secret()` still supports env fallback for non-product integrations and developer tooling. Runtime OAuth tokens remain in MongoDB via `auth/`.
- **`preferences/`**: Owner-scoped runtime preferences. Keep this small and product-facing: stable user settings such as `audio.tool_cues_enabled`, not host secrets or satellite hardware config. Values are loaded into each live `Session` on WebSocket connect and updated by `preferences.update` broadcasts.
- **`tool_router.py`**: Plugin-level semantic router. Each routable plugin owns a list of utterance vectors from `metadata.utterances`, source-controlled curated phrases under `core/routing/utterances/`, or generated-cache fallback from `core/integrations/utterance_cache.py`. Scoring is **max-pool over utterances** (not centroid) so narrow intents survive. Generated utterances are disposable runtime cache keyed by tool docs, plugin description, and sibling context; deterministic tool-name/docstring phrases are the offline fallback. `route()` returns a `set[str]` of fully-qualified tool names from plugins clearing the selected policy threshold after schema-budget fitting and optional carryover. An explicit always-on FQN allowlist is unioned into every iteration's `tools=` set. Canonical policies live in `core/routing/policies.py`; the router is modality-agnostic and the orchestrator chooses `voice_default`, `text_default`, or `system_hint` from turn state. Successful tool outputs call `record_tool_focus()` for ordinary underspecified follow-ups. Separately, when proactive content is actually delivered, the plugins already routed for its system turn are exposed once on the next user route (live connection handoff; conversation `routed_tools` restore the same handoff after a same-node reconnect); direct transcript matches are still included, and the main agent uses conversation history plus optional `reply_grounding` to decide whether any tool call is appropriate. Rendered assistant text, trigger context, and language-specific acknowledgements are not fed back through semantic routing. Supports hot-registration (`register_plugin`) and deregistration for runtime-added integrations, plus per-session route diagnostics for perf traces. Per-tool discovery for non-routed mounted tools lives in `system.search_tools`, separate from plugin-level routing.
- **`plugins/`**: Infrastructure for the Plugin Architecture (`types.py`, `registry.py`). Also houses `consent.py` (generalized approval gate — any plugin can require user confirmation for destructive ops; see resolver pattern below), `ui.py` (widget push helpers: `push_ui()`, `push_content()`, `push_receipt()`, and `delete_ui()`), and `widget_snapshots.py` (connect-time `ui.snapshot` providers for domain-owned widgets). Durable approval visibility lives in `core/pending_inputs.py`: runtime callbacks remain process-local, while pending approval rows make foreground and background waiting states visible, resolve-by-id safe, and reconnect-restorable through `PendingInputWidget` snapshots. The registry supports both filesystem-discovered plugins and programmatic registration (`register()`) for runtime-created plugins like MCP auto-bridges. Tracks a `_disabled` set (persisted to `system_config` in MongoDB) — `set_plugin_enabled()` rebuilds the capability catalog so the next turn's `tools=` set and ToolRouter both reflect the change.
- **`decorators.py`**: `@tool` attaches inject lists, signature, and return schema. Runtime injection, auth translation, and `ToolResult` unwrapping live in the capability dispatcher.
- **`context.py`**: Manages per-turn runtime context via `contextvars`: `owner_id` is the durable storage/account namespace; `connection_id`, `node_id`, `device_kind`, and optional `location_ref` describe where the turn came from. Ephemeral GPS is validated as `GeoPosition`; `resolve_current_location()` supplies coordinates to location-aware tools (fresh device GPS first; HA home only for room-bound or non-interactive device kinds such as satellites / headless turns). `resolve_search_location()` is narrower policy for soft local-search ranking: interactive devices may use the configured home only as a default search center when fresh GPS is unavailable, never as their asserted current position.
- **`context_manager.py`**: Token-aware context budget management. Three stateless functions — `count_tokens()` (tiktoken `o200k_base`), `fit_to_budget()` (two-pass trim: offloads oversized tool results in-place, then drops oldest messages to fit within `CONTEXT_MAX_INPUT_TOKENS - system_tokens - LLM_MAX_TOKENS - 10K loop_headroom`; image parts estimated at 1K tokens each), and `cap_tool_result()` (truncates large tool outputs to a preview before appending to `local_history`). Called once per turn before the capability-call loop. Returns stats forwarded to the frontend as a `context.metrics` WS message.
- **`attention/`**: Owner-level proactive delivery control — separate from session-local `soft_muted` input gating.
    - **`models.py`**: `AttentionMode` (`active | quiet | paused`), `ManualOverride` (the *only* authoritative input — the user's explicit choice, with optional `expires_at`), `AttentionState` (a derived, read-only view: effective `mode`, `source`, `expires_at`, `active_window_ids`), and `QuietWindow` (recurring quiet windows in local wall-clock time).
    - **`resolver.py`**: Pure functions. `resolve_scheduled_attention()` evaluates enabled windows at a UTC instant (cross-midnight, overlapping coalesce, DST-safe). `resolve_effective_attention()` is the single source of truth for the effective mode: a live `ManualOverride` wins, else an active quiet window, else active. No I/O.
    - **`service.py`**: Mongo-backed. Persists only the `ManualOverride` (plus a `published_mode` cache); the effective mode is *derived* on every read, never reconciled into storage. Manual `set_mode("active")` during a window writes an override bounded to the window end so the schedule resumes afterwards; timed quiet/paused expires by override `expires_at`. Publishes `ATTENTION_CHANGED` only on actual mode transitions.
    - **`reconcile.py`**: `AttentionReconcileService` — recomputes on startup, after window writes, and every 60s, emitting edge-triggered `ATTENTION_CHANGED` events when the derived mode crosses a window/override boundary.
- **`prompts/`**: YAML-based configuration for persona and capabilities, managed by `PromptBuilder`. Supports `PromptMode` gating (`FULL` for voice turns, `BACKGROUND` for in-process agents — skips voice/style/examples sections). Also houses `build_subprocess_prompt()` for SDK subprocess agents and shared context utilities (`build_background_context`, `build_conversation_context`). Supports dynamic context injection (e.g., Current Time).
    - **`protocol_context.py`**: Standalone builder for protocol execution context (steps, run metadata, execution rules). Used by the orchestrator for system-initiated protocol turns — keeps prompt construction out of the orchestration layer.

### `backend/plugins/`
- **Canonical contract**: [`PLUGIN_ARCHITECTURE.md`](./PLUGIN_ARCHITECTURE.md) defines the plugin/capability boundary. The agent loop emits structured `CapabilityCall`s through one dispatcher and invocation ledger. `.cursor/rules/plugin-tool-conventions.mdc` contains detailed authoring conventions.
- **The Tool Ecosystem**: Contains all tools (Core & External) implemented as `JarvisPlugin` classes. These are auto-discovered by the Registry.
    - **Structure**: Supports both single-file plugins (e.g., `todo.py`) and package-based plugins (e.g., `weather/`) for complex integrations.
    - **Pattern**: External integrations define a `client.py` factory, implement `register_integrations()` to self-register, and use `@tool` to inject clients—fully drop-in, no core changes needed. Dynamic plugins declare `utterances: List[str]` in metadata for the Semantic Router.
    - **Consent Gating**: Destructive tools call `require_consent()` from `core/plugins/consent.py`, which creates a durable `pending_inputs` approval row, pushes `PendingInputWidget`, and stores the executable callback only in the live process. The user confirms via `approve_pending` / `deny_pending` for voice follow-ups or `resolve_pending_input(input_id, decision)` from the widget. Used by `system.exec()`, `files.delete()`, `gmail.send_email()`, `gmail.reply_email()`, and `calendar.delete_event()`. File writes, edits, and moves execute when explicitly requested and return compact receipts. In background contexts, a `_consent_resolver` contextvar is set before execution — the resolver receives `(description, detail)` and returns `True` (execute) or `False` (skip), keeping the runtime decision invisible to the LLM and the plugin call sites unchanged. `mode="jarvis"` installs a deferred resolver that marks the task `attention="approval"`, pushes a task/widget update, and awaits the pending input. `mode="code"` remains SDK-isolated and does not use this in-process consent path.
    - **Background Agents** — see [`docs/BACKGROUND_AGENTS.md`](../docs/BACKGROUND_AGENTS.md) for the full reference: execution paths, task lifecycle, spawn flows, fan-out controls, and known quirks.
    - **Notable Plugins**: `attention.py` — owner-level proactive delivery control (`set_mode`, `mute`, `get_mode`, `resume`) plus recurring quiet windows (`set_quiet_window`, `list_quiet_windows`, `clear_quiet_window`). Routing uses plugin `metadata.utterances` only. `set_mode_for_identity()` is a non-tool fast path for local voice commands. `system.py` — pre-built OS controls (volume, apps), consent-gated shell execution with safe-prefix classification, machine diagnostics via `psutil`, and the zero-cost `think()` scratchpad tool. `files.py` — sandboxed file access (home-dir only, dotfiles blocked, binary rejected); read/search instant, write/rename return receipts, delete is consent-gated. `smart_home/` — direct Home Assistant REST + WebSocket client; product connect stores `ha_config.url` in `system_config` and `HA_TOKEN` in `CredentialStore` (resolved via `plugins/smart_home/config.py`); HA areas are the room source of truth. Tools cover setup validation (`get_setup_status`), Tuya reload/reconcile (`refresh_home_assistant`, `organize_device`), inventory search (`search_devices`), batch control/readback (`control_devices`, `get_device_states`), current-room light control (`control_room_lights` — resolves the room from turn-origin `node_id`/`location_ref`, not conversation history, so satellites handle "turn off the lights" in one turn), relative light tweaks (`adjust_lights` — reads live HA state per target; named hues such as orange/red use RGB while warmer/cooler use Kelvin only), and node→area binding (`bind_node_area` writes `ws_device_credentials.location` for durable room refs used by "in here" and scheduler `deliver_to=<room>`); client layer in `ha_client.py` covers config entries, registry writes, and deferred Tapo/Kasa config-flow REST methods; one-time setup via `backend/cli/setup_home.py` (`task setup:home`) with optional Docker bootstrap (`task setup:home:bootstrap`). `habits/` — V0 cue-based habit tracking: owner-scoped habit definitions, append-only `habit_logs`, natural name-based logging, status summaries, and check-ins scheduled through the existing trigger system. `agents/` — background agent dispatch with two execution paths. `sdk.py` abstracts the active SDK (`claude-agent-sdk` preferred, `opencode-agent-sdk` fallback). `dispatch()` exposes an explicit model-selected runtime: **`mode="code"`** spawns a subprocess via the SDK for pure file/git/shell work; **`mode="jarvis"`** runs an in-process `JarvisAgent` (`background_agent`) with full plugin access (Slack, Gmail, GitHub, calendar, email, memory) using `PromptMode.BACKGROUND`. Both paths share `BACKGROUND_AGENT_MODEL` (default `claude-opus-4-8`) and `ANTHROPIC_API_KEY`. Direct voice/text/system/headless turns always use the configured assistant model — depth requires explicit `dispatch()`. Both paths persist compact task events and push throttled progress receipts to the top-right review rail; `BackgroundTaskWidget` is opened on demand for artifacts, trace, result, and approval state. Completion still creates a `TriggerInstance` summary and publishes `TRIGGER_DUE` for voice delivery when appropriate. Tasks use **12-character alphanumeric nanoid IDs** (e.g. `k8Tm4xQ2pR7n`, from `core.id.generate_id()`) — short enough for reliable LLM pass-through. Subprocess agents receive an XML-tagged system prompt built by `PromptBuilder.build_subprocess_prompt()` with conversation context and user memories; in-process agents receive the standard PromptBuilder prompt (minus voice/style/examples) with the same plugin catalog as a voice turn via `PromptBuilder.build_background_context()`. `session_id` is captured from the first `AssistantMessage` and persisted immediately — not deferred to task completion — so `resume()` works even for cancelled or failed tasks. `resume()` continues a completed or failed subprocess task using the SDK's `session_id`, restoring the agent's full prior context (every file read, edit, and decision); **prefer `resume()` over `dispatch()`** for iterative work on the same files. In-process `mode="jarvis"` dispatches receive per-turn `reasoning_effort` when the background model supports it. Fan-out is guarded by `AGENT_MAX_DEPTH`, `AGENT_MAX_PER_SOURCE`, and `AGENT_MAX_CONCURRENT`. `automations.py` — LLM-facing tools for managing external-event `TriggerRule`s (CRUD, pause/resume, suppression, dry-run) and Composio push trigger discovery. Push trigger registration and deregistration are handled implicitly by rule create/delete — no separate lifecycle tools. Also persists `webhook_payloads` and `webhook_dedup` collections for Composio trigger delivery. `gmail/` — bespoke Gmail integration reusing the shared Google OAuth app; 10 tools (inbox query, search, full message fetch, thread view, send/reply with consent gating, draft creation, archive, mark read/unread, inbox widget); `GmailWatcher` in `services/watchers/` polls unread inbox for the automation engine.

### `backend/services/`
- **`database/mongodb.py`**: Primary persistence layer. The Motor database is opened with `CodecOptions(tz_aware=True)` so BSON datetimes decode as timezone-aware UTC (`datetime` with `tzinfo`), matching how the app writes times. Owner-scoped collections use `owner_id` as their durable namespace. `conversations` collection stores every retained message with a `source` field (`"user"` | `"system"`) and optional `embedding` (bge-small, stored at write time for user/assistant text turns; tool results excluded). System-triggered conversation rows carry `metadata.turn_id` and, when they come from a trigger instance, `metadata.instance_id`. `turn_runs` stores compact operational telemetry keyed by `owner_id + turn_id` (timings, STT counters, turn-detection metadata, delivery/source/modality, compact tool-routing summary, optional `reasoning_effort` / `reasoning_chars`), with no prompt/transcript/tool/audio content; its `origin.instance_id` mirrors trigger-origin traces for drill-down joins. `background_tasks` remains separate from normal conversation history because delegated work is a task product surface, not a user-visible turn; each task carries compact task-scoped `trace` rows alongside live `events`, receipt `activity`, artifacts, final result, plus `attention` / `pending_input` / `live_status` for the small pending-approval control surface. `pending_inputs` stores durable approval visibility and source correlation; executable callbacks are process-local and unresolved runtime-bound inputs are cancelled on restart. `habits` stores owner-scoped habit definitions with unique `(owner_id, name_key)` lookup; `habit_logs` stores append-only habit outcomes indexed by `(owner_id, habit_id, logged_at)`. `get_history()` supports `source_filter` for two-tier loading, `skip_tool_results` for callers that need to omit stored `<tool_result>` rows, `exclude_turn_types` (e.g. `reasoning` rows excluded from prompt history), and `exclude_turn_id` so the in-flight user row is not duplicated in the LLM request after early persistence. `get_collection()` is synchronous (plain dict lookup on the Motor client). Also persists: tool data, trigger rules/instances (including external automation definitions), protocols, protocol run logs, automation fired dedup records, OAuth credentials, push channel state, background agent job records, `attention_state` (one doc per owner), and `attention_schedules` (recurring quiet windows). Legacy `alerts`, `schedules`, and standalone automation definition collections are not part of the current rule schema. Indexes managed via `_ensure_indexes()` on startup, including operations lookups over `conversations(owner_id, metadata.instance_id, timestamp)` and recent trigger-instance runs.
- **`activity/` + `operations/`**: Operational visibility is split by read cost. `core.activity` is a read-only projection over `conversations`, `turn_runs`, `trigger_instances`, and `background_tasks`; it never duplicates canonical trace or lifecycle data. `/api/v1/activity/page` returns compact pointers with an opaque source-aware cursor, normalized read-side category/outcome, human source labels, and typed detail references. Each source applies owner/time/filter predicates before the deterministic merge, so one busy source cannot starve or skip another. Indexed projection is guarded by `tools/benchmark_activity_projection.py`; the 1k/10k/100k fixture gate is 400 ms p95 before considering materialization. The legacy `/api/v1/activity/` list and `jarvis.activity.recent` remain for voice/tool compatibility. `core.operations` lazy-loads detail: trigger instances follow `turn_ids` and join `conversations`, `turn_runs`, and `protocol_runs`; user and system turns start from retained trace rows. `core.operations.definitions` is the single "what you've set up" catalog over surfaced `TriggerRule`s and saved protocols. `/api/v1/operations/setups` exposes that projection and owner-scoped rule enable/pause mutations; protocols remain read-only. No `Behavior` entity, activity collection, event store, or projector daemon is introduced. Domain writes publish `activity.changed` or `operations.changed`; those events invalidate frontend reads but are not persistence.
- **Runtime logs vs. product Activity**: Python/Rust process logs, the bounded in-memory diagnostic buffer, `turn_runs`, and desktop support exports are operational support surfaces, not Activity records. Runtime logs carry available correlation identifiers (`turn_id`, `instance_id`, `task_id`, `node_id`) and sanitize control characters, secrets, prompts, and raw tool arguments before buffering. Desktop `host.log` rotates at 5 MiB with three archives. Diagnostic exports are metadata-only by default; logs and bounded snapshots require explicit user-content opt-in, and prompt dumps are always excluded. Opt-in prompt dumps are retained separately for at most seven days / 100 files.
- **`events/bus.py`**: An internal `asyncio` Event Bus for decoupled communication. Drives the **Voice Lifecycle** (Wake, Turn Start/End) and observability.
- **`core/triggers/`**: Unified trigger substrate for scheduled reminders, timers, alarms, protocol runs, system pulse escalations, automation follow-ups, and background-agent completion summaries. `TriggerRule` is durable intent (`origin`, `conditions`, `action`, `attention`, `delivery`, `freshness`) plus user-facing definition metadata (`description`, `surface`); see [`TRIGGER_AUTHORING.md`](./TRIGGER_AUTHORING.md) for the canonical authoring contract across scheduler, automations, habits, offers, and low-level rules. Trigger data has explicit boundaries: `action.reply_grounding` is the semantic frame for a proactive utterance and its immediate reply; `instance.source_event` owns concrete fire payloads; `management` owns internal domain/resource correlation; and offer-time live state is assembled into `CURRENT_STATE`. `TriggerInstance` is one materialized fire with frozen snapshots, `turn_ids` for correlated execution attempts, optional retry timer (`next_retry_at`), and lifecycle status (`pending`, `claimed`, `executing`, `awaiting_delivery`, `completed`, `delivered`, `acknowledged`, `snoozed`, `suppressed`, `expired`, `cancelled`, `failed`). `FreshnessPolicy` is the deterministic staleness contract (`expires_at`, `expire_after_due_s`, `stale_if_source_event_started`, `on_expiry`) evaluated before delivery/retry; stale work normally expires, selected deliver-by offers can `force_deliver` at the deadline, and stale pre-start calendar content (`calendar_event_started`) always expires. `due_decision.py` is the pure pre-execution gate: it composes freshness and attention delivery policy into `expire`, `suppress`, `complete`, `awaiting_delivery`, or `execute` without writing state. `delivery_policy.py` remains the lower-level routing vocabulary for channel-neutral `agent_execution` (`user_facing` / `headless`), `presentation` (`always` / `never` / `if_content`), `blocked_result`, and `delivery_tag`; it does not choose a concrete channel. `endpoint_router.py` runs after the gate allows presentation: a pure function picking one speaker-capable endpoint from live presence (`DeliveryPlan.target` `node_id` → `location_ref` → last-active speaker), keeping endpoint selection out of the gate and the orchestrator. `offer_context.py` assembles only live durable state for **offers** (`action.decision="offer"`): trigger age plus live interruptive commitments, classified on the declared attention priority axis (`requires_ack` or `urgent`/`critical` level), never on presentation (sound). **Commitments** (alarms, timers, ack-required notifications) are named presets over action/attention/delivery/freshness that deliver deterministically through the normal trigger path. **Offers** (candidate announcements such as habit debriefs) use `action.decision="offer"` and may speak, return `NO_REPLY` (`suppressed` with reason such as `offer_no_reply`), or `DEFER` (`awaiting_delivery` with reason `offer_deferred` and a jittered `next_retry_at`). `DeliveryPlan.target` is author intent set at creation: `deliver_to="anywhere"` (follow-me), `"here"` (snapshot origin `node_id`), or a bound room name (snapshot `location_ref`). Offline room targets stay `awaiting_delivery`. `TriggerScheduler` polls `trigger_instances`, atomically claims pending work before publishing `TRIGGER_DUE`, wakes timed `awaiting_delivery` retries, materializes the next recurrence from `trigger_rules`, and recovers orphaned claimed/executing instances to `awaiting_delivery` on startup. `TriggerService` owns guarded state transitions so delivery finalization cannot overwrite an already acknowledged, snoozed, cancelled, or failed instance. `awaiting_delivery` means the system could not present or an offer asked to be reconsidered later; availability and attention changes wake event-driven rows while `TriggerScheduler` wakes rows whose `next_retry_at` is due. Explicit user STOP during an active announce trigger dismisses the instance (`acknowledged` when ackable, otherwise `cancelled`) so it is not retried.
    - **Trigger vocabulary:** A **trigger** is when something fires. **Origin** is why/when it fires (`time`, `interval`, `external`, `system`). **Action** carries `decision` (`tell`, `offer`, `act`), `message`, `instructions`, `protocol_name`, optional `content_type`, and optional `reply_grounding`. **Management** identifies the internal domain/resource that owns mutation. **Source event** is the concrete fire payload. **Decision** is whether the user hears from JARV1S (`tell` always, `offer` if worth it, `act` silent). **Delivery** is physical routing (`channel`, `target`). **Attention** is whether it may interrupt now (`normal`, `urgent`, `critical`). **Freshness** is whether the trigger is still worth delivering. A **rule** is durable When/Do intent stored as `TriggerRule`. **Reminder**, **timer**, and **alarm** are user-facing scheduled notification presets. **Commitment** means a preset that must deterministically attempt delivery until acked, cancelled, or expired. **Offer** means `decision="offer"`; the model decides at fire time whether to speak, defer, or drop. A **deferred instruction** is time-based background work from `scheduler.defer` with `decision="act"` (or `offer` when later conditional reporting is desired). Rule of thumb: `tell` reports; `offer` asks; `act` does silently.
- **`automation.py`**: Background ECA (Event-Condition-Action) engine for external-origin `TriggerRule`s with dual ingestion. **Poll path**: 60s tick; watchers return items, `_evaluate_source()` handles both anticipated (fire-time → `call_later`) and reactive (immediate fire) via `trigger_mode`. **Push path**: Composio webhooks → `on_push_event()`. Bespoke Calendar push → `PushRegistry.process_notification()` → `kick_source()` for an out-of-cycle watcher poll. Gmail remains polling-only until authenticated Pub/Sub push JWT verification is implemented. Both paths share `_fired` dedup (MongoDB TTL-indexed, 24h), pause state, and `_fire` dispatch. `_fire` additionally persists `status=failed` + error to `automation_fired` on dispatch failure so `SystemPulse` can surface recent automation errors. Auto-discovers watchers from `services/watchers/`.
- **`system_pulse.py`** (Phase 9b): Optional periodic mechanical evaluator. Configurable interval (default 30 min via `SYSTEM_PULSE_INTERVAL_MIN`; opt-in via `SYSTEM_PULSE_ENABLED`). While enabled, each tick fires indexed Mongo reads in parallel via `asyncio.gather` (`trigger_instances` overdue, `trigger_instances` stuck executing, `automation_fired` recent failures, unscheduled `trigger_instances` awaiting delivery) and **does not call the LLM** unless findings are present and not already suppressed by a recent escalation (`DEDUP_WINDOW=6h`, keyed by stable `{bucket}:{id}` identifiers). Owner attention and quiet-hour schedules gate presentation later, not the mechanical scan. Outcomes (empty/suppressed/escalated) are logged to `pulse_runs` (TTL 30d).
- **`prefetch.py`** (Phase 9c): Protocol pre-renderer. Polls every `PREFETCH_POLL_INTERVAL_S` (default 60s), scans upcoming announce-mode + protocol-linked triggers inside `PREFETCH_WINDOW_MIN` (default 5 min) from both `trigger_instances` and `AutomationService.iter_upcoming_protocol_fires` (anticipated automation fires), and runs each through the injected orchestrator's `_run_headless_turn` to pre-compute the TTS-ready briefing. The orchestrator is passed in at `start()` (no module-level reach-into) and the system_context is built via `SystemTurnContext(mode="announce")` so prefetched and live runs see identical prompts. Results land in `prefetched_results`, keyed by unique `(source, trigger_id, protocol_name)` with source values like `"trigger"` and `"automation"`, plus an `expires_at` TTL index for self-heal. `_claim_slot` is single-flight via one atomic `find_one_and_update` (replace stale/failed rows) plus a fallback `insert_one` whose `DuplicateKeyError` collapses races against a fresh ready/running row. In-flight prefetch tasks are tracked and drained on `stop()`. NO_REPLY or empty responses are never cached (we'd never want to speak the sentinel). At fire time the orchestrator's `_try_prefetched_delivery(trigger_data=...)` atomically consumes the cache via `find_one_and_delete` in the announce branch; on a hit it schedules `_deliver_text` as the turn runner, preserves barge-in through `session.current_turn_task`, and settles the `TriggerInstance` through the same guarded delivery-finalization path as live voice output. On any miss / expired / fire-time drift it falls through to the live `process_turn` path. Announce-only by design — silent has nothing to pre-render; evaluate needs live evaluation.
- **`health.py`**: Reusable `IntegrationHealth` tracker for background pollers. Tracks consecutive failures per source with log-once state transitions and publishes `SYSTEM_WARNING` at a configurable threshold. Used by `AutomationService`; any future background poller should use it too.
- **`headless_pool.py`**: `HeadlessTurnPool` — bounded concurrency and task tracking for headless (non-session) agent turns. Wraps an `asyncio.Semaphore` plus an in-flight task set. `schedule()` dispatches fire-and-forget coroutines and logs exceptions. Owned as `self.headless_pool` by `AssistantOrchestrator`.
- **`watchers/`**: Thin, per-integration data providers. Each watcher polls one external source and returns current items as plain dicts — errors must propagate (never catch-and-return-empty). `CalendarWatcher` and `GmailWatcher` define `trigger_mode` (anticipated vs reactive). CalendarWatcher items include enriched fields (`is_all_day`, `attendees`, `attendee_count`, `duration_minutes`) enabling fine-grained automation conditions. New watchers are added by dropping a file here — `AutomationService` discovers them automatically via `pkgutil.iter_modules`.
- **`push/`**: Bespoke push adapters (separate from Composio). `PushRegistry` owns lifecycle (renewal timers, MongoDB persistence, restart recovery) and dispatch routing. Adapters implement `PushAdapter` Protocol (`register`, `renew`, `verify`, `on_notification`, `teardown`). Auto-discovered from `services/push/`. The production adapter is `CalendarPushAdapter` (Google Calendar Watch API); polling remains the fallback.

## 4. Design Philosophies

- **Composition over Inheritance**: The `Session` owns a `SpeechProcessor` rather than inheriting audio logic.
- **16kHz Standardization**: The entire input pipeline is 16kHz to ensure VAD/STT accuracy without backend resampling overhead.
- **Streaming First**: Every component (LLM, TTS) must support streaming to minimize "Time to First Word."
- **Progressive Tool Disclosure**: The system prompt carries global behavior only. Per-turn routing supplies JSON schemas for likely plugins via `tools=`; `system.search_tools` discovers mounted tools that were not routed this turn.
- **Endpointing Is Edge-Triggered**: VAD silence is a candidate event, not a repeated condition. `SpeechProcessor` emits one `TURN_COMPLETE` per candidate, keeps buffering during `ENDPOINT_CANDIDATE`, and emits `TURN_RESUMED` if speech returns. The handler resolves candidates in a cancellable `endpoint_decision_task`; once a candidate is accepted, that task is registered as `accepted_input_task` to cover the post-commit handoff (final STT, local-command check, and scheduling). `process_turn()` is then scheduled as `current_run_task`. Fast recovery awaits handoff when still finalizing STT, then cancels `current_run_task` if needed — same `VoiceInputTurn`, merged transcript. Keep endpoint tuning small and layered: VAD proposes quickly, audio EOU decides, and max delay remains the safety valve.
- **Delivery-Agnostic Agent Loop**: `execution.execute_turn()` runs the agent and mutates a `TurnResult`; it never touches the session, WebSocket, or TTS. A `DeliveryStrategy` decides what to do with each yielded `StreamEvent`. Voice turns use `VoiceDelivery` (WS + TTS); headless turns (silent automations, prefetch, SystemPulse) use `HeadlessDelivery`. Adding a new channel is one class, one method.
- **Presence Identity Boundary**: WebSocket presence is intentionally small and transport-scoped. Clients may send timezone and optional room `location_ref` hints, but `owner_id`, bound `node_id`, and capabilities come from the authenticated device credential at handshake time (`token -> owner_id`), not from query parameters. Ephemeral GPS is a separate later `context.update` payload, not presence identity. Persisted MongoDB owner fields use `owner_id`, keeping the durable namespace distinct from `connection_id`, `node_id`, and per-turn `speaker_id` (verified barge-in matches today; not device presence).
- **Turn-Origin Delivery**: User-initiated voice/text turns deliver on the live `connection_id` that started the turn. `ConnectionManager.get_session_by_connection()` is the only lookup on that path; passing an `owner_id` no longer silently falls back to last-connected. If that origin disconnects mid-turn, delivery stops there — no fan-out to another node. Tool follow-ons (`run_protocol`, `stop_listening`) publish `connection_id` only when it is a live WebSocket origin; background in-process agents use `owner_id` as session id and omit it so protocol output falls back to `get_default_session_for_owner()`. Proactive triggers and evaluate speech (no originating turn) resolve a concrete endpoint at fire time via `core.triggers.endpoint_router.resolve_proactive_endpoints()` over live presence: explicit `DeliveryPlan.target` `node_id` → `location_ref` → last-active speaker-capable node. If no speaker endpoint is live, the trigger stays `awaiting_delivery` rather than speaking on another node.
- **Trigger Delivery Outcomes (Phase 9a)**: Trigger delivery is resolved by `core.triggers.delivery_policy`, not by scattered orchestrator branches. `FreshnessPolicy` is checked before delivery and retry so stale work either expires or force-delivers according to `on_expiry`. `TriggerAction.decision="tell"` resolves to `user_facing` + `presentation=always`; `decision="act"` resolves to `headless` + `never`; `decision="offer"` resolves to `headless` + `if_content`. User-facing delivery marks the instance `delivered` only when audio is actually sent; no-audio or offline outcomes stay `awaiting_delivery` for signal-driven retry. Silent work completes as `completed` because no presentation was requested. Offer triggers settle as `suppressed` (`NO_REPLY` with an auditable reason), `delivered`, `awaiting_delivery` (blocked presentation, no audio, or `DEFER`), or `failed` (including harness/provider `runtime_error`, which is not treated as speakable content); `DEFER` stores a jittered `next_retry_at` so semantic defers are reconsidered even if connection and attention never change. `decision="offer"` triggers also receive live commitment context from `offer_context.py` before the headless evaluation pass. Concrete channels remain outside this policy — a future channel router can map user-facing presentation to voice, Telegram, in-app, etc. Delivery policy lives on triggers, not protocols — protocols are pure recipes and inherit from the invocation context.
- **Turn-Level Tracing**: Every turn gets a `turn_id` (nanoid, `turn-` prefix) generated at its entry point — `process_turn` for user/announce turns, `_handle_trigger_due` for trigger fires, `_handle_protocol_run` for manual protocol runs. The `turn_id` is threaded as a first-class parameter to `_persist_trace`, which stamps it on every conversation row's `metadata.turn_id`. Trigger/automation runs can produce zero or many turns, so `trigger_instances.turn_ids` is the run-to-attempt correlation list; `_handle_trigger_due` records each generated turn immediately. `PerfLogger` also aggregates the same turn into a compact `turn_runs` document for diagnostics and latency analysis. Protocol lifecycle rows in `protocol_runs` also carry the same `turn_id`, linking them to their full agent trace. Separate from `turn_id`, an optional `origin` dict carries audit fields (`trigger_source`, `instance_id`, `rule_id`, `rule_name`, `protocol_name`, `instructions`) — present on system turns, absent on user turns. Indexed on `conversations.metadata.turn_id`, `conversations(owner_id, metadata.instance_id, timestamp)`, `turn_runs.(owner_id, turn_id)`, and `protocol_runs.turn_id`. 90-day TTL on `protocol_runs`; `turn_runs` uses an `expires_at` TTL.
- **Time-Awareness**: The system is timezone-aware from the WebSocket handshake down to the tool execution, ensuring absolute time references (e.g., "14:30") are accurate to the user's location.
- **Timezone-Safe Persistence**: The Motor client opens the database with `tz_aware=True` so datetimes read from MongoDB always carry explicit UTC `tzinfo`. Application code must use `datetime.now(timezone.utc)` (or another explicit zone) for "now" and must not mix naive and aware datetimes. This invariant is enforced at the database layer rather than at each read site.
- **Structured Capability Calls**: The AI interacts with the world by emitting named JSON tool calls. Adapters produce provider-neutral model events; a wire call becomes a `CapabilityCall` only after registry name resolution.
- **Dependency Injection**: External services (APIs) are injected into tools via the capability dispatcher. Tools request what they need (e.g., `weather: AsyncClient`), and the Integration Gate provides it authenticated and ready.
- **Modular Plugin Architecture**: All tools are `JarvisPlugin` classes located in `backend/plugins/`, auto-discovered by a Registry. Plugins self-register their integrations and declare dependencies, enabling true drop-in extensibility.
- **Stateless Services, Stateful Sessions**: Services (like `LLMService`) should be stateless, while the `Session` object maintains the context of the current interaction.
- **Opinionated Tool Docstrings**: Tool descriptions are the primary interface for the LLM. They must be concise but **opinionated**, defining usage guidelines, error behaviors, and return structures (Pydantic schemas) directly in the docstring to minimize prompt burden.
- **Tools as Policy**: Tools define their own behavioral rules (e.g., "Never read coordinates aloud"). The system prompt remains focused on persona, while tools teach the agent how to use them.
- **Durable Mutation Contracts**: Tools that create or update persistent user-facing state must treat LLM-generated arguments as untrusted input. Fetch the existing record, merge partial patches through a typed Pydantic model, validate domain invariants before writing, and return an actionable `CapabilityErrorDetail` without side effects when validation fails. Shared mechanical helpers belong in `core/plugins/`; domain truth such as valid fields, ids, scopes, and provider capabilities stays with the owning plugin/service.
- **Consent-Gated Destruction**: Any plugin can gate a destructive operation behind user approval via `require_consent()`. The consent system is decoupled from individual plugins — callbacks are registered process-locally and visible approval state is stored in `pending_inputs` until explicit user resolution through `PendingInputWidget` or the voice `approve_pending()` / `deny_pending()` tools. In background contexts, a resolver function (set via `_consent_resolver` contextvar) replaces the default widget flow: the runtime decides whether to execute or skip, invisible to the LLM and plugin call sites. This makes the approval decision a first-class concern of the execution context, not an if-branch inside each plugin.
- **Durable User Input, Atomic Assistant Trace**: Accepted user input is upserted to `conversations` immediately with `metadata.turn_status="pending"` so reloads do not lose the user's submitted turn. The current `turn_id` is excluded when loading history for the same LLM request because `JarvisAgent.process_stream()` appends the live user input itself. Assistant/tool trace rows are persisted when execution completes or is intentionally interrupted, and the user row is marked `completed` or `cancelled`. Late continuation reuses the same `turn_id`, so the pending user row is updated in place with the merged transcript.
- **Token-Budgeted Context**: History loaded from MongoDB is trimmed each turn by `context_manager.fit_to_budget()` before the first LLM call. Large tool outputs are truncated to previews for the LLM's working context while the full output is preserved in MongoDB and surfaced to the frontend unchanged. Budget: `CONTEXT_MAX_INPUT_TOKENS - system_tokens - LLM_MAX_TOKENS - 10K loop headroom`.
- **Context Window as Cache**: There is no ephemeral vs. persistent distinction. Everything is stored; the context window is just a cache. User turns load recent node-scoped context with a 200-message user-source budget plus a small sanitized system tail (5 messages), bounded by the inactivity window described above. Raw system execution prompts remain audit data; delivered assistant text from visible proactive turns is merged chronologically as assistant conversation context. Noise is separated via `source`, `delivery`, and projection rules, not separate collections. `recall()` remains owner-wide and searches both archival memories and recent conversation turns for on-demand retrieval of older or cross-device context.
- **Fail-Closed Core Readiness**: Infrastructure settings are validated at startup via `pydantic-settings`. Main assistant LLM setup resolves from persisted `system_config.llm_config` and `CredentialStore`, not from `.env`. User, voice, and headless LLM turns pass through `require_llm_ready()` so missing setup blocks model work explicitly instead of failing opaquely.
